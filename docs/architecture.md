# 架构设计说明

本文档说明智能审校 Agent 的技术选型理由、多 Agent 协作机制、关键取舍与扩展方式，
面向后续维护者与评审方。

---

## 一、设计目标与约束

| 目标 | 约束 | 对应设计 |
|---|---|---|
| 稿件不出域 | 只能使用本地/内网模型，无外部 API | 模型适配层统一走内网 HTTP；嵌入模型可本地部署 |
| 审校结论必须可信 | 不能出现"模型幻觉式审校" | 硬性事实（术语、算术、格式）全部由确定性规则与算法负责；模型只做"判断/复核/撰写" |
| 误报必须极低 | 一次误报就会让编辑弃用系统 | 三级匹配 + 多重误报压制 + 独立的批评修正 Agent |
| 流程不能中断 | 内网 GPU 资源紧张，模型可能不可达 | 降级为纯规则引擎，工作流照常产出报告并标注 `degraded=True` |
| 结论可追溯可申诉 | 审校涉及责任认定 | 每条问题带规则 ID、出处、置信度、检出 Agent；全流程 trace |
| 可持续演进 | 政治术语提法会持续变化 | 术语库版本化 + 动态更新管道 + 影子校验人工审批 |

## 二、分层架构

```
┌────────────────────────────────────────────────────────────────────┐
│ 接口层    CLI (argparse) │ 库 API (ProofreadAgent) │ 可挂 Web/HTTP   │
├────────────────────────────────────────────────────────────────────┤
│ 编排层    LangGraph StateGraph                                     │
│           12 节点 · 并行 fan-out/fan-in · 条件边动态路由 · 批评修正环  │
├────────────────────────────────────────────────────────────────────┤
│ 智能体层  受理预检 │ 调度 Supervisor │ 5 个专业审校 Agent            │
│           结果汇聚 │ 批评修正 │ 事实复算 │ 修订稿生成 │ 报告聚合       │
├────────────────────────────────────────────────────────────────────┤
│ 引擎层    术语引擎 │ 语文引擎 │ 逻辑引擎 │ 专业引擎 │ 风格引擎         │
│           纯函数式：Document → List[Issue]，不做 IO、不调模型          │
├────────────────────────────────────────────────────────────────────┤
│ 基础层    文档对象 │ 文本算法 │ 术语库 │ 规则库 │ 本地模型适配 │ 报告渲染 │
└────────────────────────────────────────────────────────────────────┘
```

**关键分层原则：引擎层与模型层解耦。**
引擎是纯函数，因此可以：离线运行、单元测试、逐条复现、被任意 Agent 组合调用。
模型只在"规则覆盖不到的语义边缘"与"需要自然语言输出"的地方出现。

## 三、为什么是"规则 + 模型"混合，而不是纯 LLM 审校

纯 LLM 做审校在生产环境有三个致命问题：

1. **不可复现**：同一稿件两次运行结果不同，编辑无法信任，也无法申诉。
2. **幻觉**：模型会"发明"并不存在的术语规范，或漏掉明确的红线表述——政治术语审校中
   漏报的代价远高于误报。
3. **不可审计**：无法回答"为什么判这句有问题"。

因此本系统把审校拆成两类任务：

| 任务类型 | 举例 | 由谁负责 |
|---|---|---|
| 有确定答案的判定 | 术语写法对错、组合提法顺序、分项之和是否等于合计、文献年份是否越界 | **确定性规则/算法**（可复现、可解释、零幻觉） |
| 需要语义判断 | "以人民为核心"是否等价于"以人民为中心"、某个批评是否成立、如何改写更严谨 | **本地模型**（输出带置信度，且可被 Critic 驳回） |

模型产出的每一条判断都必须经过 Critic 复核；模型不可用时整条链路自动降级，不产生
"半成品结论"。

## 四、共享状态（State）设计

LangGraph 的状态是 Agent 之间唯一的信息交换通道，其设计决定了并行安全性与可观测性。

```python
class AuditState(TypedDict, total=False):
    doc, doc_type, style_preset            # 输入
    settings, store, llm                   # 运行时依赖（传递引用，不参与计算）

    route, route_reason, defects_profile   # 调度（由 Supervisor 写入）

    engine_results:  Annotated[Dict, merge_dict]    # 各引擎结果，key 隔离，并行安全
    issues:          Annotated[List, extend_list]   # 并行召回，累加
    reviewed_issues: Annotated[List, last_value]    # 批评修正后的定稿，覆盖

    llm_review, llm_issues                 # 模型产出
    critic_notes, critic_round, suppressed_ids
    fact_check                             # 确定性复算记录
    report, trace                          # 终态与审计轨迹
```

**三个 reducer 的用途**

* `merge_dict`：五个 Agent 各写自己的 key（`engine_results["terminology"]` 等），
  浅归并即可，天然避免写冲突；
* `extend_list`：`issues` 由并行分支累加，配合报告阶段的去重与重叠消解；
* `last_value`：`reviewed_issues` 是"覆盖式"语义——Critic 的输出代表对召回结果的
  最终裁定，必须替换而不是追加，否则会出现"被驳回的问题又回来了"。

> 这个区分是本项目踩过的真实坑：早期版本 Critic 直接写回 `issues`，
> 由于 reducer 是 `extend_list`，导致每轮批评后问题数量翻倍。

## 五、节点契约与职责

| 节点 | 职责 | 关键实现 |
|---|---|---|
`intake_agent` | 文档解析、特征统计、依赖探测、**病灶画像** | 统计政治词密度/数据点数/论证标记/参考文献数，推测文体倾向 |
`supervisor_agent` | 动态路由 | 依据画像与稿件类型输出激活清单；`route_fn` 返回节点名列表触发并行 fan-out |
`terminology_agent` | 政治术语审校 | 三级匹配引擎；对低置信度（L2/L3）命中调用模型复核，模型判误报则丢弃 |
`language_agent` | 语文规范审校 | 规则库（31 条示例）+ 标点/数字/冗余/长句/全半角专项检查 |
`logic_agent` | 逻辑严密性 | 六类缺陷检测；对 MAJOR 级缺陷请模型给出改写示范 |
`academic_agent` | 专业深度审校 | 数据算术自洽、格式、三层查重、GB/T 7714 文献校验 |
`style_agent` | 风格迁移 | 量化画像 + 目标区间比对 + 迁移动作清单 + 受控改写示范 |
`join_agent` | 同步屏障 | 汇聚并行分支，统计各引擎召回量 |
`critic_agent` | **误报压制** | ①规则自检 ②同位置冲突消解 ③模型复核高严重度问题 ④第二轮保守收敛 |
`fact_check_agent` | 确定性复算 | 对数据/文献/红线术语问题重算并标注信源，产出可作签发依据的记录 |
`revision_agent` | 修订稿生成 | 仅自动应用"安全修改"，高风险问题只留痕不改稿 |
`report_agent` | 聚合与门禁 | 去重、维度评分、签发门禁、摘要生成、报告构建 |

### 关键节点细化：批评修正环

```
join ──► critic ──┬── 仍有 FATAL/MAJOR 且轮次 < max ──► critic（第二轮：保守收敛）
                  └── 否则 ──► fact_check
```

Critic 在架构上被刻意设计为**"驳回者"**：它的 KPI 不是"找更多问题"，而是
"删掉站不住脚的问题"。三条压制规则：

1. **规则自检**：建议等于原文、区间为空、定位漂移（区间文本与记录内容无包含关系）→ 剔除；
2. **冲突消解**：同一位置多条互斥建议，按 `严重度 → 置信度 → 建议具体程度` 保留一条
   （例如"布署"同时被术语库与错别字规则命中，保留置信度更高的术语条目）；
3. **模型复核**：逐条问本地模型"这条批评是否成立"，模型驳回且给出理由则降级为
   `[模型复核存疑，建议人工确认]` 并记录驳回理由——保留申诉通道，而非直接删除。

第二轮采用更严格的收敛策略：丢弃置信度 < 0.6 且非高严重度的问题。

## 六、并行 fan-out / fan-in 的实现细节

LangGraph 中条件边可以返回**节点名列表**，从而在运行时触发并行 fan-out：

```python
builder.add_conditional_edges(
    "supervisor_agent", supervisor.route_fn,
    {n: n for n in SPECIALIST_NODES},
)
for node in SPECIALIST_NODES:
    builder.add_edge(node, "join_agent")
```

**同步屏障（barrier）语义的坑**：若某个分支本轮未被激活（例如短稿不需要风格检查），
它不会触发，而 `join_agent` 有 5 条入边——很容易出现"等待一个永远不会执行的节点"。
本项目的处理方式是：

* 五个专家节点**始终**被调度，但未激活的节点在 `execute` 开头立即返回，
  只写一条 `skipped=True` 的 trace，不产生任何计算；
* 这样既保证了屏障语义，又让"被跳过"在报告里可见（编辑能看到"本轮未激活"）。

实测（示例稿件 1393 字）：全流程 12 节点、5 路并行，端到端 **< 100 ms**（纯规则引擎），
其中专业深度 Agent 因要加载语料库与三层查重耗时最长（≈65 ms）。

## 七、五大引擎的关键算法

### 7.1 政治术语三级匹配

```
L1 精确：Aho-Corasick 自动机（标准表述 + 全部错误变体）
         → 一次线性扫描命中全部模式，不受正则元字符影响，支持重叠命中
L2 近似：字符二元组倒排索引投票 → 候选位置 → 带上界剪枝的 Levenshtein 验证
         → 捕获未登记的字形错误（别字、漏字、增字）
L3 语义：本地嵌入向量 + 余弦相似度，对比术语条的"语义种子"
         → 捕获"字面完全不同但政治含义偏移"的表达
```

**L2 的边界误报防护**（实战踩坑）：`习近平新时代中国特色社会主义思想为指导`
与变体 `……思想体系` 仅尾部两字不同，编辑距离 2、相似度 0.895，会被误判。
解决方案是加一条硬规则：**若窗口内包含任一完整标准表述（长度 ≥ 6），直接跳过**。

### 7.2 误报压制策略（生产的生命线）

| 策略 | 规则 | 理由 |
|---|---|---|
| 引述豁免 | 仅在**长引述**（引号内容 ≥ 20 字）内豁免 | 短引号内的术语短语恰恰是错误高发处，不能放过 |
| 否定语境豁免 | 命中位置前 8 字含"不得/禁止/避免"等 | "不得使用 X"中的 X 不是错误 |
| 参考文献区豁免 | 文献题名不可改 | 引注他人题名不承担修改义务 |
| 标准表述保护 | 命中片段本身是某标准表述 → 降级为提示 | 防止"把正确的改错" |
| 重叠消解 | 同区间只保留 `严重度 → 匹配长度 → 规则特异性` 最高者 | 同一处不刷多条相似提示 |

### 7.3 数据自洽性复算

以**段落**（而非句子）为分析单元——中文公文中"分项—合计—占比"三者常跨句表述：

> 2026 年上半年，共归集数据 862 万条……其中，民政数据 312 万条，社保数据 268 万条，
> 卫健数据 196 万条，三项合计 776 万条，占归集总量的 95.8%。

算法：数值解析为 `(标签, 数值, 单位, 起止偏移)` 四元组 →
以"其中/分别为"与"合计"提示词切分**分项集合**（这一步避免把上一句的
"总费用 420 万元"误当作"三项合计 440 万元"的分项）→ 复算合计与占比 →
与文中声明值比对，偏差超容差即报，并给出**复算公式**作为证据。

实测可稳定捕获：分项之和 ≠ 合计、占比 > 100%、占比与所列数据不符。

### 7.4 三层查重（核心观点重复发表）

```
段落 SimHash（汉明相似度 < 0.5 直接淘汰）
   ↓
MinHash 签名（128 perm，k=5 shingle）估算 Jaccard
   ↓
字符 3-gram Jaccard
   ↓
加权融合：0.25·SimHash + 0.35·MinHash + 0.40·3-gram
```

既做**文内自我重复**，也与 `data/corpus/` 历史稿件库比对，识别"一稿多发"。
输出相似度分值、对照段落与来源文件名，供人工判定——**系统不下"学术不端"的结论**。

## 八、评分与签发门禁

维度得分采用指数衰减，避免"问题多就一律零分"的退化：

```
score = 100 · exp(−penalty / scale)      penalty = Σ 严重度权重
权重：FATAL=100  MAJOR=20  MINOR=5  INFO=1
尺度：政治 150 ｜ 语文 130 ｜ 逻辑 200 ｜ 专业 200 ｜ 风格 120
```

综合分 = 维度加权（政治 0.35、专业 0.25、语文 0.18、逻辑 0.17、风格 0.05）。

**签发门禁**

| 门禁 | 条件 | 处置 |
|---|---|---|
| `BLOCK` | 存在任一 FATAL | 不予签发，必须修改后重审 |
| `REVIEW` | 综合分 < 75 或 MAJOR > 5 | 退改后再审 |
| `PASS` | 其他 | 可通过审校 |

政治维度权重最高，因为它是"一票否决"维度。示例稿件（30+ 处埋点错误）的运行结果：
综合 **48.8 分 / BLOCK**；政治术语 23.9、语文规范 54.0、逻辑 70.5、专业 55.7、风格 95.9。

## 九、扩展指南

| 需求 | 扩展点 | 说明 |
|---|---|---|
| 新增术语 | `data/terminology/*.yaml` 或走 `terms approve` 流程 | 无需改代码，热更新即时生效 |
| 新增语文规则 | `semantic_clusters.yaml → language.*` | 支持正则可选组 + 模板化替换建议 |
| 新增一类审校 | 继承 `BaseEngine` → 实现 `run()` → 包装成 `EngineAgent` → 注册到 Supervisor | 约 60 行代码；引擎必须保持纯函数 |
| 换模型 | `config/settings.yaml → llm` 或环境变量 `PFRD_LLM__*` | 支持 Ollama / OpenAI 兼容端点 |
| 接企业语料库 | `data/corpus/` 或改写 `AcademicEngine._load_corpus` 为向量库检索 | 当前为文件级语料，可平滑替换为 Milvus/pgvector |
| 人工介入 | 挂 `langgraph.checkpoint` + `interrupt_before=["revision_agent"]` | 状态全为可序列化对象，支持人在回路 |
| 服务化 | 在 `ProofreadAgent` 上包 FastAPI | 引擎无全局状态，可水平扩容 |

## 十、已知限制与技术债

1. **术语库需持续运营**。示例库覆盖高频项，生产环境必须建立"术语更新—影子校验—人工审批"
   的常态化流程与责任岗位，否则术语库会随时间失效。
2. **无嵌入模型时语义召回下降**。`embedding_mode=lexical` 只能做词形近似，
   报告中有显式标注；建议生产环境部署 `bge-m3` 或 `bge-large-zh-v1.5`。
3. **查重语料的规模**。当前为段落级暴力比对（含 SimHash 粗筛），语料达十万段落级时
   需引入 LSH 分桶或向量索引。
4. **长文档的窗口化**。目前将全文作为整体处理；超长文本（>5 万字）建议先分章处理以控制内存。
5. **逻辑缺陷检测是启发式的**。它给出的是"需要补充论据/限定范围"的线索而非判定，
   置信度普遍在 0.7–0.88 区间，报告中如实呈现。
